全文 · Bedrock 架构设计

#0. 一句话结论 + 决策速览

一句话结论：一个人当董事会，十几个 AI 人物当员工。

  • 骨架确定，AI 只做判断。 公司的骨架是确定性的流程和规则，AI 只在需要判断的地方干活。
  • 一扇门。 每个 AI 人物在 AgentCore 上有独立的身份、会话沙箱和预算，只能通过一扇门（AgentCore Gateway + Policy） 调用工具和查询知识。
  • 四道闸。 对外、花钱或改规则的动作，执行前都要依次通过：自检 → 规则 → 护栏 → 独立复核。R3 级动作还要 Owner 批准。
  • 系统执行，全程留痕。 高风险动作由系统按批准时的载荷原样执行，人物自己碰不到高风险工具。事后全量留痕、抽样审计。

三条最重要的设计约束

  1. 账号就是爆炸半径。
    • 事实：2026年10月 Zenity 披露了 AgentCorruption 攻击链（✅[A25]）：
      1. 一条提示让带 HTTP 或 shell 工具的 Agent 访问 microVM 元数据服务，拿到执行角色的凭据。
      2. 默认执行角色覆盖同账号、同区域的所有 AgentCore 资源，于是攻击者能调用其他 Agent、读所有对话、投毒记忆、取走密钥。
    • AWS 的立场：这是"已记录的预期行为"，最小权限由客户负责（✅[A7][A25]）。
    • 对策：
      • 把接触原始外部内容的人物、掌握业务工具的人物、负责复核的人物，分放在三个不同账号。
      • 把控制面（Gateway、Policy、密钥）放进一个不跑任何 LLM 人物的账号。
      • 人物不配通用的 shell 或 HTTP 工具，每个人物一个最小权限的执行角色。
  2. "允许做什么"和"决定做什么"分开（NIST 2026年 Agent 身份原则，✅[N1]）。
    • 模型只负责"提议"。
    • 能不能做，由 Cedar 规则和流程状态机决定。
    • R2 及以上的动作由执行器按批准时的载荷执行。人物在 Policy 里根本没有这些高风险工具的权限。
  3. 唯一的人是最大的单点。
    • 审批疲劳、出差生病、被钓鱼，都会直接变成公司风险。
    • 对应设计：
      • 审批分批处理，并有防疲劳指标。
      • 放宽规则有 24 小时冷静期。
      • Owner 缺席时自动进入安全模式。
      • 设一组连 Owner 批准也越不过的硬红线（R4）。

决策速览

# 决策点 选择 主要理由 门类型
D1 底座 Bedrock（模型、知识库、护栏）+ AgentCore（Runtime、Gateway、Policy、Identity、Memory、Observability、Evaluations、Registry） 研究文档的默认推荐。13 项 AgentCore 服务在 us-east-1、us-east-2、us-west-2 全部可用（✅[A2]） 双向（换底座代价中等）
D2 账号结构 8 个账号：管理、日志、安全、平台（控制面）、边缘人物、核心人物、保障人物、预发 账号是 AWS 里最强的隔离边界；复核者不能和被复核者在同一账号 单向（事后拆账号代价高）
D3 业务骨架 Step Functions 标准工作流（状态机 + 回调审批） 托管、免运维，最适合一人公司。研究 v0.1 写的是 Temporal，这里改掉 双向
D4 人物框架 默认 Strands Agents 跑在 AgentCore Runtime 上；简单人物以后可以改用 Harness 骨架已经由状态机负责，人物内部只需要工具调用循环。Harness 本身就基于 Strands（✅[A8]），迁移成本低。研究 v0.1 写的是 LangGraph，这里改掉 双向
D5 人物协作 工作单 + 事件（黑板模式），人物之间不自由对话 对应研究原则"只有一个数据源"；可审计；防止错误连锁扩散 双向
D6 工具接入 所有工具都经 Gateway（MCP）；人物没有直接外网，也拿不到密钥 一扇门：统一认证、授权和留痕 单向（原则级）
D7 授权 AgentCore Policy（Cedar，默认拒绝，forbid 优先，✅[A13]）；阈值只在一个 YAML 里定义 规则是确定的、可测试的，不依赖提示词 双向
D8 高风险执行 "AI 提议、系统执行"：执行器校验载荷哈希后执行 杜绝"批的是 A、做的是 B" 双向
D9 RAG Bedrock 知识库放在 RAG 服务之后；租户过滤由服务端注入 换模型、换人物都不用重建知识；租户隔离不靠模型自觉 双向
D10 记忆 AgentCore Memory 按"租户 × 人物"划分命名空间；CRM 是客户事实的唯一来源 防止跨客户串数据和记忆投毒 双向
D11 模型 多模型分档；复核者和制作者用不同的模型家族；锁定版本 减少相关性错误；成本能算到每个人物 双向
D12 护栏 Bedrock Guardrails 三层强制：
- 组织级 Bedrock 策略
- 执行角色上的条件键
- 请求级岗位护栏
外部内容另用输入标记单独检测		 - 内容层防护对任何模型都适用
- 提示词攻击过滤只检测打了标记的内容（✅[B6]）		 双向
D13 审计 自建审计账本，脱敏后写入日志账号的 S3 Object Lock（合规模式） CloudTrail 只覆盖 AgentCore 的 Gateway 和 Registry（✅[A21]），不够用 单向（保留期锁定后不能缩短）
D14 治理框架 NIST AI RMF + 三道防线 + 治理即代码（Git） 研究文档第9节：在得州 TRAIGA 下，按 NIST AI RMF 治理可以作为免责依据 双向

#1. 范围、假设与设计目标

#1.1 "一人全AI公司"指什么

  • 人：只有 1 名，叫 Owner。
    • 法律上是公司的所有者和负责人；运营上是董事会、唯一的审批人和例外处理人。
    • 研究文档 9.9 列出的"必须由人办的事"都由 Owner 来做：注册公司、开银行账户和 Stripe、实名认证、报税、电话推销登记、买保险。
  • AI 人物（persona）：其余岗位全部由 AI 担任，按传统公司的部门和三道防线来组织，见第2节。
    • 每个人物都是一名受治理的数字员工，不只是一段聊天提示词。
    • 它有岗位说明书、身份、权限、预算和 KPI，也有上岗、晋升、停职、退役的流程。
  • 外部专业人士：得州律师和 CPA 不是员工。他们按季度或年度复核合同模板、合规材料和账目，属于第三道防线。

#1.4 本期不做

  • 中国大陆的业务和区域。
  • 自训或微调模型：第一年用不上 SageMaker（研究文档 5.9）。

两条组织规则

  1. 幕僚长AI 只管派工和盯 KPI。
    • 它不能给任何人物加权限、改规则或批准高风险动作。
    • 原因：管理者人物最容易被利用来提权，这是 OWASP Agent 十大风险里的"身份和权限滥用"。
  2. 第二、三道线独立于第一道线。
    • 它们直接向 Owner 汇报，不接受幕僚长的调度。
    • 它们和被复核的人物不在同一个账号里。

#3.3 流程为骨，AI 为肉

每一步的要点

  1. 骨架签发令牌（平台账号）。
    • 工作单令牌是短期的，用 KMS 非对称密钥签名，里面有工作单 ID、租户 ID、人物 ID 和风险上限。
    • Step Functions 的任务令牌只存在平台账号的 DynamoDB 里，永远不交给人物，所以人物伪造不了流程推进。
  2. 派工和路由。
    • 派工 Lambda 用 IAM 身份调用人物的 Runtime，并按比例在 prod 和 canary 两个端点之间分流。Runtime 本身没有原生的金丝雀发布（✅[A6]）。
    • 会话 ID 由工作单派生。AgentCore 不负责把用户和会话绑定起来（✅[A3]），这件事要自己做。
  3. 令牌对模型不可见。
    • 人物外壳代码把工作单令牌放进 Gateway 请求头，模型看不到它，也改不了它。Gateway 拦截器能读到请求头（需要开启 passRequestHeaders，✅[A12]）。
    • 人物调用 Gateway 用的 JWT，通过 AgentCore Identity 的客户端凭据获取。凭据的访问权按工作负载身份限定（✅[A17]）。
  4. 请求拦截器（每个 Gateway 最多一个请求拦截器和一个响应拦截器，✅[A12]）负责三件事：
    • 校验工作单令牌的签名、有效期，以及令牌里的人物是否就是 JWT 的主体。
    • 用令牌里的租户 ID 覆盖参数里的租户。原则是"租户上下文来自流程，不来自模型"。
    • 对执行器的调用，核对审批记录。
    • AWS 在 2026-11-12 的博客里推荐同样的做法：在拦截器里注入经过验证的身份，再叠加 Cedar 策略（✅[B4]）。
    • 拦截器和 Policy 谁先执行，⚠️ 需要实测确认。设计上两者各自独立都能拦住越权调用。
  5. 响应拦截器处理外部来源的工具结果（网页、邮件、客户文档、知识片段）：
    • 用 InvokeGuardrailChecks 给提示词攻击打分（✅[B16]），分数高就截断，并标记为可疑。
    • 原因是 Guardrails 的提示词攻击过滤不扫描工具结果，也不作用于知识库检索出的片段（✅[B6][B5]）。
  6. 交回结果：人物调用 workitem___submit，平台校验 JSON Schema 后代为执行 SendTaskSuccess。

G-12 RCP 全部 S3、KMS、Secrets Manager、DynamoDB、SQS、ECR、CloudWatch Logs、STS 只接受本组织主体访问。RCP 不支持 Bedrock、AgentCore、Lambda、Step Functions 和 SES（✅[S2]），这些靠资源策略和 SCP 数据流到外部账号
G-13 预算动作 Workloads OU 月预算用到 120% 时，自动挂一条拒绝模型调用和 Runtime 调用的 SCP。这是 AWS 推荐的 Bedrock 花费封顶做法（✅[B9]） 成本失控（拒绝钱包攻击）

样例写法见 bedrock-reference-artifacts.md。

G-01 的细节

  • US 地理推理配置文件从 us-east-1、us-east-2、us-west-2 发起时，会路由到这三个区域。只要有一个目标区域被 SCP 拒绝，请求就会失败（✅[B10]）。
  • 全球推理配置文件大约便宜 10%（✅[B10]），但请求可能落到美国以外的区域。本设计用成本换数据驻留，要放开需要 Owner 决定。

#4.3 网络

  • 人物没有直接外网。
    • 三个人物账号的 Runtime 都用 VPC 模式，放在私有子网，不配 NAT（✅[A5]）。
    • 它们只通过接口端点访问 AWS：
      • ECR（api、dkr）和 S3（网关端点）：无外网的 VPC 必须有这三个（✅[A5]）。
      • bedrock-runtime。
      • bedrock-agentcore：数据面，含 Memory 和 Identity。
      • bedrock-agentcore.gateway（✅[A22]）。
      • CloudWatch Logs、STS。
    • 就算人物被注入了指令，也没有通道把数据发到攻击者的服务器。
    • 注意：VPC 里的任何代码都能读到执行角色的凭据，和网络模式无关（✅[A7]）。所以凭据本身也要防，见 G-09 和 9.2。
  • 唯一的外部出口在平台账号的工具层。
    • 工具 Lambda 通过 NAT 出网，配 Route 53 Resolver DNS 防火墙，只放行白名单里的 SaaS 域名（CRM、Stripe、电子签等）。
    • 第二阶段可以再加 AWS Network Firewall，但每个可用区每月约 $290 起（📚），要权衡成本。
  • 网页研究只给边缘区人物，用 AgentCore Browser 的隔离会话（PUBLIC 网络模式，✅[A23]）。边缘区人物手里没有机密数据，被诱导访问恶意网址也带不走什么。
  • 代码执行只在 Code Interpreter 的 SANDBOX 模式下进行，外部访问受限（✅[A23]）。人物不配通用的 shell 和 HTTP 工具，这是 AgentCorruption 的直接入口（✅[A25]）。
  • 接口端点费用：每个端点每个可用区每小时 $0.01（✅[S6]），约合每月 $7.3。
    • 3 个人物账号 × 约 7 个端点 × 2 个可用区，每月约 $300。
    • 想省钱有两个办法：
      • staging 只用 1 个可用区。
      • 用 RAM 共享 VPC 集中端点（⚠️ 待确认 AgentCore VPC 模式是否支持共享子网）。
  • 端点策略的限制：接口端点策略只能约束 IAM 主体，用 OAuth 认证的调用方只能写 Principal: *（✅[A22]）。所以 Gateway 的访问控制主要靠 JWT 和 Policy，不靠端点策略。

#5. AI 人物运行设计（AgentCore）

#5.1 运行方式选型

方式 是什么 本设计怎么用
AgentCore Runtime + 自己的代码 自己的 ARM64 容器（放 ECR）或直接部署代码；框架任选（✅[A3][A8]） 默认：所有人物共用一个用 Strands 写的"人物运行时"镜像，每个人物只是配置不同
AgentCore Harness 托管的 Agent 循环，基于 Strands。用配置定义模型、提示词、工具、技能、记忆和上限；跑在 Runtime 里，不单独收费；有生命周期钩子，可以挂一个 Lambda 来做放行或拒绝（✅[A8]） 第二阶段用来把简单人物"配置化"，前提是两件事：
1. 确认它调用 Gateway 时能带上工作单令牌（⚠️）。
2. 只允许 Bedrock 做模型提供方。它也支持 OpenAI、Gemini 和兼容接口，但那样数据会离开 AWS，护栏和日志也覆盖不到
经典 Bedrock Agents — 不用：可控性和可移植性都不如前两种

共用镜像的外壳代码

下面这些是每个人物都必须有的，写在外壳代码里，不交给提示词：

  1. 处理工作单令牌：
    • 校验令牌，并且不让它进入模型上下文。
    • 把它放进每一次 Gateway 调用的请求头。
    • 用它派生会话 ID 和记忆命名空间。
  2. 预算熔断：
    • 每次调用的 token 上限。
    • 每次会话的工具调用次数上限，防止死循环。
    • 会话最长存活时间。Runtime 允许在 60 到 28,800 秒之间配置（✅[A4]）。
    • 每天的预算上限。
  3. 标记不可信内容：
    • 把外部原文放进 Converse 的 guardContent 块；用 InvokeModel 时套上随机后缀的标签。
    • 没有标记，提示词攻击过滤就不生效（✅[B6]）。
  4. 结构化输出：用 JSON Schema 校验，失败最多重试 2 次，然后升级。
  5. 可观测性：
    • 用 OpenTelemetry 打点。
    • 通过 Bedrock 的 requestMetadata 带上人物 ID 和工作单 ID，让调用日志能和其他记录关联起来（✅[B12]）。
  6. 只给 Gateway 上的工具：
    • 不配 Strands 自带的 shell、http_request 这类通用工具。
    • 生产AI另外可以用 Code Interpreter 沙箱。

2 岗位卡 使命、KPI、边界、升级规则 Git personas/ 不能

  • 第1、2层对每个人物是固定的，适合做提示词缓存。
    • 以 Claude Fable 5.2 为例，缓存读取每百万 token $0.20，正常输入是 $8（✅[B22]）。
    • 缓存最少 512 个 token，有效期可以选 5 分钟或 1 小时。
  • 人物不能修改自己的提示词和规则。 想沉淀经验，走第8节的变更流程，不靠记忆"自我进化"。

#5.3 协作：用工作单，不聊天

  • 人物之间不直接对话，而是通过工作单交接。
    • 工作单是带 JSON Schema 的结构化产物，存在骨架里。
    • 幕僚长AI创建和分派工作单。每次交接都是状态机里的一次状态转换。
  • 第一阶段不开 A2A，虽然 Runtime 支持它（✅[A3]）。
    • 以后如果要开，只开只读的咨询类调用，而且同样经过 Gateway 和 Policy。
  • 好处：
    • 每次交接都有记录、有格式。
    • 错误不会在人物之间口口相传。这对应 OWASP 的两项风险："错误连锁扩散"和"不安全的 Agent 间通信"。

规则

  1. 锁定模型 ID，用 us. 前缀的地理推理配置文件。
    • 升级模型属于"放宽"类变更：先跑完全部评估集，再做金丝雀发布。
  2. 数据保留模式是选模型的硬条件。
    • 处理客户机密数据（K4）的人物，只用允许 none（零数据保留）的模型。
    • 如果要用 aws_review 模式的模型，就必须在隐私政策和数据处理协议里披露。
    • 每个模型允许的保留模式要在上线前逐个确认（⚠️）。
  3. 成本归到人物：每个人物有独立的 IAM 角色，用 CUR 2.0 按 IAM 主体统计，再配 AWS Budgets 的拒绝动作。这是 AWS 推荐的做法，可以避免给每个人物建应用推理配置文件、造成配置文件泛滥（✅[B9]）。
  4. 降级模型：每个人物配一个降级模型。主模型不可用时降级，或者进入安全模式。
  5. 不用 Intelligent Prompt Routing：它只支持 Nova Lite、Nova Pro 和 Llama（✅[B14]），覆盖不了本设计的主力模型。

#5.5 会话、记忆与租户隔离

会话

  • 一次会话对应"一个租户的一张工作单"。
  • Runtime 给每个会话一台独立的 microVM，会话结束后销毁，内存清零（✅[A3]）。

记忆的设置

  • 每个人物账号一个 Memory 存储。
  • 策略：
    • 启用"摘要"和"用户偏好"两种长期策略。
    • 不启用"情节"（episodic）策略。经验沉淀走治理流程，不让人物悄悄学习（✅[A18]）。
  • 命名空间：
    • 格式是 /tenant/{tenantId}/persona/{actorId}/，其中 tenantId 是自定义命名空间键，最多可以有 5 个（✅[A18]）。
    • 外壳代码从工作单令牌里取出 tenantId，模型指定不了。
    • 执行角色用 IAM 条件键 bedrock-agentcore:namespacePath 限定，人物只能访问带有自己 persona 段的路径。
  • 保留期：
    • 短期事件 30 天（最长可以设 365 天）。
    • 长期记录 365 天（最短 31 天）（✅[A18]）。

隐私删除和事实来源

  • 删除要做全：DeleteEvent 不会删除从事件里提取出来的长期记录（✅[A18]）。所以隐私删除流程必须对这个租户的命名空间执行 BatchDeleteMemoryRecords。
  • CRM 是客户事实的唯一来源。 记忆只存互动摘要和偏好，不存价格、合同状态这类事实；这些要用时去 CRM 实时查。

#5.6 发布与版本

  • 版本和端点：Runtime 的版本不可变。prod 和 canary 是两个命名端点，需要手动切换指向（✅[A6]）。
  • 金丝雀发布：派工 Lambda 按比例分流，例如 10% 的工作单发给 canary。
  • 发布流程：
    1. 预发环境跑完评估集。
    2. 金丝雀发布，在线评估抽样打分（见 8.4）。
    3. 指标达标后，把 prod 指向新版本。
    4. 回滚时把 prod 指回旧版本，几秒钟就能完成。
  • 依赖版本：
    • AgentCore SDK、CLI 和 Strands 都锁定在 2026 年各个 CVE 修复之后的版本（✅[A26]）。其中 CVE-2026-15737 的问题是旧版 SDK 把原始提示词写进了追踪数据。
    • 生产环境不用 Starter Toolkit，它有代码注入和 SSRF 漏洞（CVE-2026-105812、CVE-2026-106032）。一律用 IaC 部署。

#6.3 关键决策

1. 知识库类型：用 Bedrock 托管知识库。

选项 优点 缺点
托管知识库（默认） AWS 现在推荐的类型（✅[B1]）。
- 永远是混合检索（关键词 + 语义）。
- 内置解析、托管嵌入、托管重排都免费。
- 价格：索引每 GB 每月 $5，检索每千次 $1（✅[B3][B14]）。
- 不用运维向量库，最适合一人公司		 - 切分只支持默认、固定大小、不切分三种。
- 元数据过滤不支持 startsWith 和 stringContains（✅[B3]）
自管知识库 + Aurora PostgreSQL（pgvector） 支持混合检索；切分方式更多（分层、语义） 要运维数据库
自管知识库 + OpenSearch Serverless 支持混合检索 有最低容量费用
自管知识库 + S3 Vectors 最便宜，2025年12月已 GA（✅[S7]） 在知识库里只能做语义检索；元数据最多 1 KB、35 个键（✅[B2][B3]）

托管知识库的切分和过滤限制，对第一年的语料规模（几 GB）没有实质影响。真遇到瓶颈，再换成 Aurora pgvector：入库流水线和检索工具的接口不变。

2. 三个知识库，一个知识库对应一个检索工具。

  • 三个检索工具：knowledge___search_company、knowledge___search_governance、knowledge___search_customer。
  • 这样 Cedar 在"动作"这一层就能管住"哪个人物能查哪个知识域"，不需要解析参数。

3. 只检索，不让知识库代为生成。

  • 检索工具调用 Retrieve 接口，返回分数和出处，人物引用时要用。
    • 11月9日新增的"只检索模式"属于 AgenticRetrieveStream，它返回的片段不带分数和出处（✅[B20]），所以不用它做业务检索。
  • 由人物自己生成回答，再用 Guardrails 的上下文溯源检查核对回答和片段是否一致（✅[B6]）。
  • 单次 RAG 和 agentic 检索（每千次 $4 加底层检索费，✅[B14]）可以留给 Owner 的研究问答。

4. 租户隔离（四层）。

  1. 服务端注入过滤条件。 拦截器从工作单令牌里取出租户 ID，注入元数据过滤条件，模型指定不了租户。
    • AWS 的说法是：元数据过滤是"关键的安全边界"，必须由应用代码每次都加上。
    • AWS 在 2026-11-12 的博客里明确说：不要让 LLM 选择用户；要在 Gateway 拦截器里注入经过验证的身份，再叠加 Cedar 策略（✅[B4]）。
    • 托管知识库自带的"按访问权限检索"（userContext）不算授权机制，不能依赖它（✅[B4]）。
  2. 返回前逐条复核。 检索工具检查每个片段的 tenantId 和分级；有任何不符就整批丢弃，并且告警（失败即关闭）。
  3. 每周做跨租户探测。 用 A 客户的令牌去查 B 客户才有的内容，泄漏率必须是 0。
  4. 合同要求更强隔离的客户，单独一个知识库（或者一个独立的向量索引）。AWS 也建议受监管的场景按租户分索引（✅[B4]）。

5. 检索结果也是不可信的。

  • Guardrails 不作用于检索出来的知识库片段（✅[B5]）。
  • 防线有三道：
    1. 入库时做注入扫描（6.4 第③步）。
    2. 响应拦截器给片段打提示词攻击分数（3.4）。
    3. 人物把片段放进 guardContent，当作数据而不是指令。

6. 检索质量。

  • 混合检索 + 托管重排。
  • 分数低于阈值时宁可回答"不知道"，然后升级。
  • 对客户说的每一条事实都要带出处，复核官会核对。

7. 新鲜度。

  • 每份文档都带版本、生效日期和状态元数据。
  • 检索时固定加上 status = active 过滤。
  • 知识管理员AI每周出一份"过期、冲突文档"报告。

8. 人和 AI 共用一套知识。

  • AWS Quick 可以直接接 Bedrock 知识库（研究文档 5.8 ✅）。
  • Owner 想用对话方式查公司知识时可以选配它，不用再建一套。

复核官的独立性要满足五条，缺一不可

  1. 和制作者不在同一个账号（agents-assurance）。
  2. 和制作者用不同的模型家族。
  3. 直接看原始出处和规则，不只听制作者的说法。
  4. 制作者交过来的内容只当"数据"处理；复核官的指令只来自它自己的岗位卡和评分表。
  5. 每月由 Owner 给 20 条复核结论打标签，做校准。复核官和 Owner 的一致率低于 95% 时，复核官本身要整改。

#7.5 AI 提议、系统执行

  • 人物在 Cedar 里根本没有高风险工具的权限。 R2 及以上的工具（发送报价、发起合同、退款、公开发布、付款）只有执行器能调用。人物只能调用 action___propose。
  • 执行器的流程（执行器是平台账号里的确定性代码）：
    1. 审批记录里保存：载荷的 SHA-256 哈希、批准人、规则版本、过期时间、"只能用一次"的标记。
    2. 执行器调用工具前重新计算载荷哈希，必须和审批记录一致。
    3. 请求拦截器再核对一次审批记录。
    4. Gateway 的 Policy 做最后一道检查：调用者是不是执行器；金额有没有超过硬上限。
  • 可选的第二把锁：Dogwood 时序策略（✅[A16]）。
    • 规则是：执行器在同一个策略会话里，1 小时之内先调用过 approval___verify，返回结果是"已批准"，而且审批 ID 一致，才放行 refund___process。
    • 前提条件是：请求带上策略会话 ID 头，而且调用方和 Gateway 在同一个账号、同一个区域。执行器和 Gateway 都在平台账号，满足条件。
    • 写法见样例文件。
  • 好处：
    • 不会出现"批的是 A，做的是 B"，也就是检查时和执行时不一致的问题。
    • 人物就算被注入了指令，也够不着高风险工具。

#7.6 Owner 的审批体验

  • 审批卡片包含：
    • 要做什么：原文，以及和模板的差异。
    • 为什么做：理由和出处链接。
    • 风险等级。
    • 复核官的意见。
    • 能不能撤回。
    • 要花多少钱。
    • 什么时候过期。
  • 按钮：批准、修改后批准、驳回，以及"批准并提议改规则"。最后一个会生成一个规则变更 PR，以后同类事情就不用再批。
  • 节奏：
    • 每天两个固定时段批量处理，例如 9:00 和 16:00。
    • 只有阻塞客户的 R3 才实时推送，推送内容里不放敏感信息。
  • 过期：72 小时没处理就自动驳回，同时告诉客户"需要更多时间"。永远不会默认放行。
  • 防审批疲劳：
    • 统计每一类审批的通过率和平均用时。
    • 某一类连续 200 次以上、通过率超过 98% 时，系统会提议降低这类事项的审批级别。这个提议本身也要走变更流程。
    • 平均审批用时少于 5 秒时，提醒 Owner"可能在走过场"。
  • 渠道安全：
    • 只能在登录后的控制台里审批，登录要用通行密钥。
    • 不接受回复邮件审批，因为邮件可以伪造。

5. 金丝雀发布
6. 全量发布
紧急 事件处理中的临时变更 破窗：Owner 用硬件密钥执行，72 小时内补上复盘和 PR

一个人怎么做职责分离

传统的职责分离需要两个人。这里用四样东西代替"第二个人"：

  1. 机器当第二把钥匙：复核官和合规官在别的账号、用别的模型家族。
  2. 时间当第二把钥匙：放宽类变更有冷静期。即使 Owner 被钓鱼或者一时冲动，也有 24 小时可以反悔，期间系统会反复提醒。
  3. 记录不可篡改：Owner 自己的操作也写进审计账本，删不掉。
  4. 外部第三方：律师和 CPA 每季度或每年复看一次。

另外，Owner 日常登录的身份只有"审批人"和"只读"权限，没有 AWS 管理员权限。基础设施只能通过流水线修改，见 G-07 和 G-08。

#8.5 模型治理

  • 白名单：只允许 G-03 列出的模型。每个模型在 Registry 里登记用途、版本和数据条款。

  • AI 身份告知：
    • 人物可以有名字，例如"Ava，X 公司的 AI 助理"。
    • 但第一次接触时和邮件签名里都必须说明自己是 AI，并且随时可以转给真人（Owner）。
    • 不使用真人的名字和照片。
    • 相关法规：
      • 欧盟 AI 法案第50条（有欧盟客户时）。
      • 加州 BOT 法。
      • 科罗拉多聊天机器人法（2027 年起）。
      • 得州 DTPA 的误导风险。
      • 见研究文档第7、9节。
  • 已批准宣传用语库（K5）：
    • 所有对外的能力、效果和价格说法，都必须出自这个用语库。
    • 复核官会逐条核对。
    • 这是防 DTPA 误导性宣传的主要手段。
  • 外联合规：
    • 遵守 CAN-SPAM：真实的发件人、退订链接、及时处理退订（📚）。
    • 退订名单是 Cedar 策略里的一个条件，命中就拒绝发送。
  • 隐私：
    • 得州 TDPSA 下的访问和删除请求，由合规官AI受理、Owner 批准执行。
    • 删除范围包括记忆（见 5.5）。
  • 记录保留：见第10节，具体年限要律师确认。
  • 风险台账：每个用例对应适用的法规和控制措施，每季度复看一次。

  • G-07 规定策略只能由流水线修改，以防有人悄悄放宽。

  • 所以 K1–K4 都是拦截器和风险引擎读取的"只收紧"开关。

  • 自动触发只能收紧，不能放宽。 恢复一律由 Owner 操作。
  • 哨兵AI自己也可能被诱导乱按开关，造成拒绝服务。所以：
    • 它每小时最多触发 3 次。
    • 每次触发都通知 Owner。
    • K5 不归它管。
  • 每次事件都要复盘，产出三样东西：新的评估用例、规则变更、知识修订。

  • 隐私删除和不可篡改审计的矛盾：
    • 审计账本只存 ID、哈希、决定和规则版本，不存邮件正文和个人信息。
    • 全文放在可以删除、保留期较短的地方。
    • 这样删除请求能执行，审计链也完整。
  • 模型的数据保留模式：见 5.4 和 8.5。处理客户机密数据的人物只用允许零保留的模型。

#9.5 运行与网络隔离

  • 会话隔离：每个会话一台 microVM（✅[A3]）。
  • 沙箱：不可信代码只在 Code Interpreter 沙箱里跑，网页只在 Browser 会话里打开。
  • 出网：人物没有外网（4.3）。唯一的出口是平台账号工具层的 DNS 防火墙白名单。
  • 公网入口：全部在 CloudFront + WAF 之后；SaaS 回调要验签。

#9.6 资金安全

控制点 做法
收款 Stripe 受限密钥，只给开票和查询类权限
退款 只能由执行器发起，额度见 7.3；超过上限只能 Owner 在 Stripe 后台手工处理
付款 人物碰不到银行账户。付供应商用虚拟卡，设单笔和每月上限，只能付给已登记的供应商；登记新收款方属于 R4，只能 Owner 走冷静期

频率 Cedar + 计数器，限制每天的退款笔数和金额

#9.7 邮件与域名

  • 两个域名：主域名和外联子域名分开，外联子域名被拉黑也不影响主域名。
  • 认证：配置 SPF、DKIM、DMARC，DMARC 策略设为 p=reject。
  • 发件地址：每个人物有自己的发件地址；Cedar 规定人物只能用自己的地址发信。
  • 收信校验：收到的邮件保存 SPF、DKIM、DMARC 的校验结果。没通过校验的邮件，一律不当作客户指令处理。

#9.8 检测与响应

  • 安全服务：GuardDuty（含 S3 恶意软件防护）、Security Hub、Config、IAM Access Analyzer，结果汇总到 security-tooling 账号。
  • 控制面变更告警：
    • CloudTrail 只记录 AgentCore 的 Gateway 和 Registry（✅[A21]）。
    • 对 Gateway、目标、拦截器和策略引擎的任何变更都告警。
    • 每小时检查一次策略引擎是不是还在 ENFORCE 模式。
  • AI 专项告警：
    • 某个人物的 token 用量、工具调用频率、Policy 拒绝次数、护栏拦截次数突然升高。
    • 跨租户探测失败。
    • 金丝雀文档出现在对外内容里。
  • 处置流程：告警 → EventBridge → 哨兵AI分诊 → 按剧本收紧（K1–K4）→ 通知 Owner。

#9.9 供应链

  • Python 依赖：走 CodeArtifact 私有仓库，锁定版本和哈希。
  • AgentCore SDK、CLI 和 Strands：锁定在 2026 年 CVE 修复之后的版本。生产环境不用 Starter Toolkit（✅[A26]）。
  • 镜像：放 ECR，开启 Inspector 扫描，并签名；每个镜像生成 SBOM。
  • MCP 服务器和工具：只能从 Registry 白名单里选，并锁定版本。MCP 协议版本也要锁定，因为 2026 年 7 月的新版本不向下兼容（研究文档第2节）。
  • 不从任何"技能市场"直接安装：OpenClaw 的技能市场出现过恶意技能（研究文档第8节）。

#11. 可靠性与 DR

按常见的灾备分级思路：

  • 等级：Tier 3，同区多可用区 + 跨区备份。RTO 24 小时，RPO 1 小时（💡）。
  • 多可用区：Step Functions、DynamoDB、Lambda、AgentCore、Bedrock 这些托管服务本身就跨多个可用区。
  • 备份：
    • DynamoDB 开启时间点恢复（PITR），并用 AWS Backup 跨区复制到 us-west-2。
    • 知识源文件和审计账本用 S3 跨区复制。
  • 重建：
    • 全部基础设施用 IaC 描述。
    • AgentCore 的全部服务在 us-west-2 都可用（✅[A2]），所以可以在 us-west-2 整体重建。
    • 知识库从 S3 重新同步即可。
  • 模型容量：
    • US 地理推理配置文件本身就在三个美国区域之间路由（✅[B10]）。
    • 每个人物另配一个降级模型。
  • 区域故障时：
    • 进入 K4 安全模式。
    • 用 us-west-2 的 SES 发自动答复（两个区域都支持收发信，✅[S5]）。
  • AI 的"灰色故障"：
    • 模型被悄悄更新、知识库发生漂移，都会让质量慢慢变差，但系统表面上看起来一切"正常"。
    • 用质量金丝雀（8.4）来发现这类问题。分数下降就自动降级到 A1。
    • 这类"灰色故障"是传统灾备演练覆盖不到的，要单独监测。

护栏成本

  • Guardrails 按文本单位计费，而 Agent 每轮循环都会把整段对话历史再发一遍。
  • 所以，如果对全部消息做检测，成本会随着轮数的平方增长。
  • 建议的做法：
    • 组织基线默认用"只检测打了标记的内容"（selective）。
    • 外壳代码只给新进来的外部内容打标记。
    • 只有 agents-edge 账号设成"全量检测"（comprehensive），作为兜底（✅[B7]）。

和研究文档的关系

  • 研究文档里"一步到位版"每月 $3,000–20,000 是全口径，包括 SaaS 和人工监督。本表只算 AWS 部分。
  • 搭建费仍按研究文档的 $15–40 万估算。如果 Owner 本人就是架构师，再配一名自由职业工程师，可以压到区间的下沿。

主要的省钱手段

  • 提示词缓存。
  • 按档位选模型。
  • 护栏只放在边界上。
  • staging 只用 1 个可用区。
  • 评估共享 VPC 来集中接口端点（⚠️）。
