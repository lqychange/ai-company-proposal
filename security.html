安全防护

一句话：假设每个 AI 人物迟早会被注入恶意指令，然后保证它被攻破了也动不了钱、改不了规则、读不到其他客户的数据。

#2026 年发生过的真实事件（✅）

  • OpenAI Dots：连续处理 10 个任务时 19.7% 出现中度越权；第三方测试发现它会批准自己被标记的动作。
  • Meta Muse：能看到其他用户的信息、会暴露文件系统；macOS 零日漏洞。
  • Grok Bot：同一账号下所有 bot 共用凭据；同公司的命令行工具上传了用户的整个代码仓库。
  • AWS AgentCore：Zenity 的"AgentCorruption"——一条提示就能接管同账号同区域的所有 Agent。
  • 开源供应链：常用组件 LiteLLM 在 2026 年 3 月被植入后门；OpenClaw 技能市场出现恶意技能，2.8 万多个实例暴露在公网。
  • Paperclip：12 个安全公告，其中 2 个截至 11-13 仍未标注修复版本。

#威胁模型

对照 OWASP Agent 应用十大风险（2025-12 发布）：

威胁 在这家公司里怎么发生 主要控制
ASI01 目标劫持 / 提示词注入 客户邮件、网页、附件、知识片段里藏着指令 隔离读信员；不可信内容打标记；网关响应拦截器打分；人物没有外网；高风险工具不在人物手里
ASI02 工具滥用 人物用合法工具做不该做的事 Cedar 参数级规则；频率限制；执行器
ASI03 身份和权限滥用 幕僚长或被注入的人物给自己提权 每个人物独立身份；人物账号禁止 IAM 写操作；放宽类变更有冷静期
ASI04 供应链 依赖包被投毒；恶意 MCP 服务器 私有包仓库 + 锁定版本；镜像扫描和签名；MCP 只用白名单
ASI05 意外代码执行 人物被诱导执行任意命令 不给通用 shell/HTTP 工具；代码只在沙箱里跑
ASI06 记忆和上下文投毒 恶意内容进入长期记忆或知识库 入库注入扫描；按知识域审批；关闭"情节记忆"；每周抽查
ASI07 不安全的 Agent 间通信 人物之间互相传话，放大错误或注入 用工作单 + 格式校验交接；不开放自由对话
ASI08 错误连锁扩散 一步错、步步错 状态机分段；每段都有闸；质量金丝雀
ASI09 利用人对 Agent 的信任 Owner 疲劳时随手批准；伪造的审批邮件 审批卡片附复核意见；防疲劳指标；只能在控制台审批
ASI10 失控的 Agent 死循环、乱花钱 预算熔断；K1–K5 熔断
同账号横向接管 读元数据服务拿到凭据，调用其他 Agent 三个人物账号分开；最小权限执行角色；凭据只能在运行环境里用；只有派工角色能调用人物
悄悄关掉授权 有人把策略改成"只记录"模式 只允许流水线修改；变更告警；每小时检查是否在拦截模式
Owner 被盗号或被社工 钓鱼；深度伪造的"客户来电" 通行密钥 + 硬件密钥；R4 硬红线；冷静期
拒绝钱包 攻击者诱导人物大量调用模型 每个人物的预算；WAF 频率限制；预算动作

核心是"双 LLM 模式"：读不可信内容的模型（隔离读信员），碰不到任何能力；有能力的模型，只看结构化字段。另外，对外内容里不能出现未登记的链接和外部图片，防止通过链接把数据带出去。

#八层防护

层 做什么 本方案怎么做
1 身份 每个 Agent 独立身份、短期凭据、最小权限、随时可撤销 每个人物一个执行角色 + 一个网关身份；一键停职
2 工具调用网关 所有工具调用都经过网关，按规则放行 Gateway + Policy + 拦截器 + 执行器
3 输入输出护栏 防注入、隐藏个人信息、过滤内容、核对事实 组织级 + 岗位护栏；隔离读信员
4 运行隔离 每个会话独立沙箱，只能访问白名单 每会话一个 microVM；人物没有外网；三个人物账号
5 资金 虚拟卡，设单笔和每日额度 见下文
6 检测与响应 发现异常行为，定期红队 GuardDuty、Security Hub；AI 专项告警；哨兵AI + 熔断
7 供应链 锁定依赖版本、私有仓库、白名单 私有包仓库；镜像签名和 SBOM；不从任何技能市场直接安装
8 数据 不保留数据、控制存放地区、加密、客户隔离 分级加密；数据不出美国；零保留模型；客户隔离四层

#资金安全

控制点 做法
收款 Stripe 受限密钥，只给开票和查询类权限
退款 只能由执行器发起，额度按授权矩阵；超过上限只能 Owner 在 Stripe 后台手工处理
付款 人物碰不到银行账户。付供应商用虚拟卡，设单笔和每月上限，只能付给已登记的供应商；登记新收款方属于 R4
频率 规则 + 计数器，限制每天的退款笔数和金额

#邮件与域名

  • 两个域名：主域名和外联子域名分开，外联子域名被拉黑也不影响主域名。
  • 认证：SPF、DKIM、DMARC，DMARC 策略设为 p=reject。Gmail、雅虎和微软都已强制要求认证，投诉率要低于 0.1% ✅。
  • 发件地址：每个人物有自己的发件地址，规则规定人物只能用自己的地址发信。
  • 收信校验：没通过 SPF/DKIM/DMARC 校验的邮件，一律不当作客户指令处理。

#数据分级

分级 例子 谁能访问
公开 服务目录、公开价格 所有人物
内部 SOP、话术、指标 按岗位
机密 规则、合同模板、财务 指定的人物 + Owner
客户机密 客户资料、客户记忆、交付物 只有处理该客户工作单的人物
受限 模型调用全文日志、追踪数据、审计账本 审计角色 + 内审AI（只读）

隐私删除和不可篡改审计的矛盾：审计账本只存 ID、哈希、决定和规则版本，不存正文和个人信息；全文放在可以删除、保留期较短的地方。这样删除请求能执行，审计链也完整。
