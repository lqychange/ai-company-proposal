#3. Cedar 策略（AgentCore Policy）

写法依据（✅[A13][A14]）

  • 主体：AgentCore::OAuthUser::"<JWT sub>"。用 Cognito 客户端凭据模式时，sub 就是这个应用客户端的 ID（📚）。
  • 动作：AgentCore::Action::"<目标名>___<工具名>"。不支持通配符，可以用列表。
  • 资源：AgentCore::Gateway::"<gateway-arn>"。
  • 工具参数：在 context.input 里。Schema 里是 integer 的字段对应 Cedar 的 Long；是 number 的字段要用 decimal() 比较。
  • 默认拒绝，forbid 优先。

容易踩的坑：Cedar 里一条策略的条件如果求值出错（比如访问了不存在的字段），这条策略会被跳过。对 forbid 来说，跳过就等于没拦。所以 forbid 里要先用 has 判断字段在不在，缺字段时按"拒绝"处理。

// ① 销售AI：可以查三个知识库（客户知识的租户过滤由拦截器注入）
permit(
  principal == AgentCore::OAuthUser::"{{personas.ae.client_id}}",
  action in [
    AgentCore::Action::"knowledge___search_company",
    AgentCore::Action::"knowledge___search_governance",
    AgentCore::Action::"knowledge___search_customer"
  ],
  resource == AgentCore::Gateway::"{{gateway_arn}}"
);

// ② 销售AI：只能"提议"发送报价和合同，不能自己发
permit(
  principal == AgentCore::OAuthUser::"{{personas.ae.client_id}}",
  action == AgentCore::Action::"action___propose",
  resource == AgentCore::Gateway::"{{gateway_arn}}"
)
when {
  context.input has action_type &&
  ["quote_send", "contract_send"].contains(context.input.action_type)
};

// ③ 高风险工具只有执行器能调用。forbid 优先，任何 permit 都覆盖不了
forbid(
  principal,
  action in [
    AgentCore::Action::"quote___send",
    AgentCore::Action::"contract___send",
    AgentCore::Action::"refund___process",
    AgentCore::Action::"payment___pay_bill"
  ],
  resource == AgentCore::Gateway::"{{gateway_arn}}"
)
unless { principal == AgentCore::OAuthUser::"{{executor.client_id}}" };

// ④ 执行器退款：必须带审批 ID，金额不超过 Owner 上限
permit(
  principal == AgentCore::OAuthUser::"{{executor.client_id}}",
  action == AgentCore::Action::"refund___process",
  resource == AgentCore::Gateway::"{{gateway_arn}}"
)
when {
  context.input has approval_id &&
  context.input has amount_cents &&
  context.input.amount_cents <= {{thresholds.refund_cents.owner_max}}
};

// ⑤ R4 硬上限：超过上限，或者缺少金额字段，一律拒绝（连 Owner 批准过的也不行）
forbid(
  principal,
  action == AgentCore::Action::"refund___process",
  resource == AgentCore::Gateway::"{{gateway_arn}}"
)
when {
  !(context.input has amount_cents) ||
  context.input.amount_cents > {{thresholds.refund_cents.owner_max}}
};

// ⑥ 获客AI：只能用已批准的模板，只能用自己的发件地址
//    退订名单是动态数据，由工具 Lambda 检查，不放在 Cedar 里
permit(
  principal == AgentCore::OAuthUser::"{{personas.sdr.client_id}}",
  action == AgentCore::Action::"email___send_outreach",
  resource == AgentCore::Gateway::"{{gateway_arn}}"
)
when {
  context.input has template_id &&
  context.input has from &&
  {{cedar_set(thresholds.outreach.approved_templates)}}.contains(context.input.template_id) &&   // 渲染为 ["tpl-intro-v3", "tpl-followup-v2"]
  context.input.from == "{{personas.sdr.mailbox}}"
};

// ⑦ 登记新收款方是 R4：通过 Gateway 谁都不能做。只能 Owner 在银行或卡平台后台操作，并走冷静期
forbid(
  principal,
  action == AgentCore::Action::"payment___add_payee",
  resource
);

可选：用 Dogwood 时序策略加第二把锁（✅[A16]，写法改编自官方示例）

  • 规则：执行器必须在同一个策略会话里、1 小时之内，先调用过 approval___verify 并且返回"已批准"，审批 ID 也要一致，才能退款。
  • 前提：
    • 请求带上 x-amzn-bedrock-agentcore-policy-session-id 头。
    • 调用方和 Gateway 在同一个账号、同一个区域。
    • 会话空闲 24 小时就会过期。
  • 注意：这条策略要替换上面第 ④ 条，不能两条同时存在。几条 permit 之间是"或"的关系，同时存在的话，没有经过时序验证的请求也能被第 ④ 条放行，时序锁就形同虚设。第 ⑤ 条硬上限照样保留。
  • ⚠️ 一条策略里能不能同时写普通的 when 和 when temporal，要实测。不行的话，就把审批 ID 和金额的检查都放进执行器和拦截器里做。
permit (
    principal == AgentCore::OAuthUser::"{{executor.client_id}}",
    action == AgentCore::Action::"refund___process",
    resource == AgentCore::Gateway::"{{gateway_arn}}"
)
when temporal {
    formerly within 1h AgentCore::Action::"approval___verify"::response{
        eventResource:     resource,
        input.approval_id: context.input.approval_id,
        output.approved:   true
    }
};

策略测试：每条策略都配"应当允许"和"应当拒绝"两组用例，放在 policies/tests/，流水线里跑。策略还要在 LOG_ONLY 模式下跑过一段时间，确认没有误拒，再切到 ENFORCE（主设计 9.8 规定 ENFORCE 模式要每小时检查一次）。

#4. 组织级护栏和 IAM

#4.1 G-01 区域白名单 SCP（含 US 跨区推理豁免）

写法依据（✅[B10]）

  • US 地理推理配置文件会把请求路由到 us-east-1、us-east-2、us-west-2。只要有一个目标区域被拒，请求就会失败。
  • 可以用 bedrock:InferenceProfileArn 豁免这种路由。
  • 全球配置文件要求放行 aws:RequestedRegion = "unspecified"。本设计故意不放行，以保证数据不出美国。

这样写能做到

  • us-east-1、us-west-2 照常可用。
  • us-east-2 只放行经由 us.* 推理配置文件路由过来的 Bedrock 调用。
  • 其他区域，以及全球推理配置文件，一律拒绝。

两点说明

  • 同一个 Deny 语句里的两个条件是"与"的关系。对非 Bedrock 请求来说，bedrock:InferenceProfileArn 这个键不存在，StringNotLike 的结果为真，所以照样会被拒绝。
  • ⚠️ NotAction 里的全局服务列表，要按 AWS 官方的区域限制 SCP 范例补全。上线前用真实调用验证。
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "organizations:*", "sts:*", "account:*", "support:*", "health:*",
        "budgets:*", "ce:*", "cur:*", "cloudfront:*", "route53:*", "wafv2:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "us-west-2"] },
        "StringNotLike":   { "bedrock:InferenceProfileArn": "arn:aws:bedrock:*:*:inference-profile/us.*" }
      }
    }
  ]
}

#4.3 G-02 组织级护栏（Bedrock 策略，策略类型 BEDROCK_POLICY）

写法依据（✅[B7]）

  • 护栏要建在管理账号里，每个区域一份，并且要发布数字版本。
  • 要给护栏加一条资源策略：用 aws:PrincipalOrgID 允许组织内调用 bedrock:ApplyGuardrail。
  • 成员账号的角色需要有 bedrock:ApplyGuardrail 权限。
  • 组织级护栏里不能包含自动推理策略，否则运行时会失败。
  • 多个挂载点按"声明式继承"合成一份生效策略，不是取并集。可以用 DescribeEffectivePolicy 查看最终结果。

挂法

  • Workloads OU：默认只检测打了标记的内容（selective），这样成本可控（主设计第12节）。
  • agents-edge 账号：单独挂一份，把 messages 改成 comprehensive（全量检测）。
  • us-west-2：同样配置一份，供 DR 使用。

执行器的核心逻辑（伪代码）

载荷用 RFC 8785（JSON 规范化）序列化后再算哈希，保证同一份载荷每次算出的哈希都一样。

def execute(approval_id: str, payload: dict) -> dict:
    rec = approvals.get(approval_id)
    if rec is None or rec["status"] != "approved":
        raise Denied("not approved")
    if utcnow() > parse_time(rec["expires_at"]):
        raise Denied("approval expired")
    if sha256(jcs_canonicalize(payload)) != rec["payload_sha256"]:
        raise Denied("payload differs from what was approved")
    # 条件写入：只有 used 还是 false 时才能改成 true，保证一个审批只能用一次
    approvals.mark_used(approval_id, condition="used = :false")
    ledger.append(event="execute", approval_id=approval_id, tool=rec["tool"],
                  payload_sha256=rec["payload_sha256"], rule_version=rec["rule_version"])
    return gateway.call_tool(rec["tool"], payload,
                             headers={"x-approval-id": approval_id})  # 请求拦截器会再核对一遍

#6. Step Functions：R3 审批片段

依据：.waitForTaskToken 只在标准工作流里可用，专门用于人工审批这类场景（✅[S1]）。

流程

  • approval-request Lambda 做两件事：
    1. 把任务令牌存进 DynamoDB。令牌不发给人物，也不发给 Owner。
    2. 生成一张审批卡片。
  • Owner 在控制台操作后，控制台后端调用：
    • 批准：SendTaskSuccess。
    • 驳回：SendTaskFailure，错误码填 Rejected。
  • 72 小时没人处理就超时，自动驳回，不会默认放行。

#7. 隔离读信员的输出 Schema

设计要点

  • 读外部内容的人物只能输出这个结构，意图只能从枚举值里选。
  • 任何字段都没有能直接驱动工具的自由文本。

路由规则（由骨架执行，不由模型决定）

  • 意图是 legal_threat 或 complaint，或者请求里包含 refund、delete_my_data：进 R3 队列，同时通知合规官AI。
  • 以下任一情况转人工队列：
    • injection_suspected = true
    • confidence < 0.7
    • sender.auth = fail
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "InboundMessageExtraction",
  "type": "object",
  "additionalProperties": false,
  "required": ["message_id", "sender", "intent", "requested_actions", "injection_suspected", "confidence"],
  "properties": {
    "message_id": { "type": "string" },
    "sender": {
      "type": "object",
      "additionalProperties": false,
      "required": ["email", "auth"],
      "properties": {
        "email": { "type": "string", "format": "email" },
        "auth":  { "enum": ["pass", "fail", "none"] }
      }
    },
    "intent": {
      "enum": ["new_inquiry", "reply_to_quote", "support_request", "billing_question",
               "unsubscribe", "complaint", "legal_threat", "spam", "other"]
    },
    "entities": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "company":    { "type": "string", "maxLength": 200 },
        "budget_usd": { "type": "number", "minimum": 0 },
        "deadline":   { "type": "string", "format": "date" }
      }
    },
    "requested_actions": {
      "type": "array",
      "maxItems": 5,
      "items": { "enum": ["send_info", "schedule_meeting", "send_quote", "change_contract",
                          "refund", "cancel", "delete_my_data"] }
    },
    "summary":             { "type": "string", "maxLength": 600 },
    "injection_suspected": { "type": "boolean" },
    "confidence":          { "type": "number", "minimum": 0, "maximum": 1 }
  }
}

sender.auth 不由模型判断，而是由收信 Lambda 根据 SPF、DKIM、DMARC 的校验结果填写，然后覆盖模型的输出。
